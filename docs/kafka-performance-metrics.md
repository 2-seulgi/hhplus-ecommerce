# Kafka 기반 시스템 성능 개선 지표

이 문서는 기존 시스템(AS-IS)과 Kafka 기반 시스템(TO-BE)의 성능 비교를 제시합니다.

**⚠️ 중요: TO-BE 지표는 예상값입니다** (실제 측정은 부하 테스트 후 업데이트 예정)

---

## 1. 전체 시스템 비교

### 1.1 핵심 성능 지표

| 메트릭 | AS-IS (Redis/동기) | TO-BE (Kafka/비동기) | 개선율 |
|--------|-------------------|---------------------|--------|
| **주문 API 응답시간** | 2-3초 | **1초** | 60-66% 개선 |
| **쿠폰 발급 처리량** | 100 TPS | **300 TPS** | 200% 증가 |
| **시스템 가용성** | 95% (장애 전파) | **99%** (장애 격리) | 4% 개선 |
| **확장성** | 제한적 | **선형 확장 가능** | - |
| **메시지 유실률** | 0.1% (Redis AOF) | **0%** (Kafka Replication) | 완전 제거 |

## 2. 주문/결제 시스템 상세 비교

### 2.1 응답시간 분석

#### AS-IS: 동기 처리

```
주문 생성: 200ms
├─ DB 저장: 50ms
├─ 알림 전송: 1000ms  ← 외부 API 호출
└─ 데이터 플랫폼 전송: 1200ms  ← 외부 API 호출

총 응답시간: 2,450ms (평균 2.5초)

문제점:
- 외부 시스템 지연이 사용자 응답에 직접 영향
- 알림 실패 시 주문 전체 롤백
- 단일 실패 지점
```

#### TO-BE: 비동기 처리 (Transactional Outbox)

```
주문 생성: 200ms
├─ DB 저장 (Order + Outbox): 100ms
└─ 응답 반환

총 응답시간: 300ms → **최대 1초** (안전 마진 포함)

백그라운드 처리 (비동기):
├─ Outbox Poller (5초마다): Kafka 발행
└─ Kafka Consumer: 독립적 처리
    ├─ 알림 전송 (1초)
    └─ 데이터 플랫폼 전송 (1.5초)

개선 효과:
✅ 사용자 응답시간 60% 단축 (2.5초 → 1초)
✅ 외부 시스템 장애 격리
✅ 장애 시에도 주문 유지
```

### 2.2 처리량 비교

| 구분 | AS-IS | TO-BE | 비고 |
|------|-------|-------|------|
| **단일 인스턴스 TPS** | 50 | 100 | 외부 API 병목 제거 |
| **3개 인스턴스 TPS** | 150 | 300 | 선형 확장 |
| **최대 확장 가능 TPS** | 200 (한계) | 1,000+ | 파티션/Consumer 증가 |

### 2.3 장애 복구 시간 (MTTR)

| 장애 유형 | AS-IS | TO-BE | 개선 |
|-----------|-------|-------|------|
| **알림 시스템 장애** | 전체 주문 중단 | 주문 정상, 알림만 지연 | ✅ 장애 격리 |
| **데이터 플랫폼 장애** | 전체 주문 중단 | 주문 정상, 데이터만 지연 | ✅ 장애 격리 |
| **Kafka 브로커 장애** | N/A | Outbox 재시도 (자동 복구) | ✅ 자동 복구 |
| **평균 복구 시간 (MTTR)** | 30분 (수동) | **5분** (자동) | 83% 단축 |

## 3. 쿠폰 시스템 상세 비교

### 3.1 처리량 비교

#### AS-IS: Redis Stream 단일 Consumer

```
단일 Consumer 처리량:
- 폴링 주기: 100ms
- 배치 크기: 10개
- 초당 처리: ~100 TPS

문제점:
- Consumer 1개로 제한 (확장 불가)
- 이벤트 배포 불가 (알림, 로그, 통계)
- Redis 장애 시 메시지 유실 위험
```

#### TO-BE: Redis Stream + Kafka (Hybrid)

```
Redis Stream Consumer:
- 폴링 주기: 100ms
- 배치 크기: 10개
- 초당 처리: ~100 TPS (변함 없음)

Kafka 파티셔닝 (userId 기반):
- 파티션 수: 3개
- Consumer 수: 3개 (각 Consumer Group별)
- 총 처리량: 300 TPS (100 x 3)

추가 장점:
✅ 이벤트 배포 가능 (알림, 로그, 통계)
✅ Kafka 영구 저장 (Replay 가능)
✅ 새로운 Consumer 추가 용이
```

### 3.2 확장성 비교

| 파티션 수 | AS-IS (Redis Only) | TO-BE (Redis + Kafka) |
|-----------|--------------------|-----------------------|
| **1개** | 100 TPS | 100 TPS (동일) |
| **3개** | 100 TPS (확장 불가) | **300 TPS** |
| **6개** | 100 TPS (확장 불가) | **600 TPS** |
| **12개** | 100 TPS (확장 불가) | **1,200 TPS** |

**핵심**: Kafka 파티셔닝으로 선형 확장 가능

### 3.3 지연시간 비교

| 단계 | AS-IS | TO-BE | 변화 |
|------|-------|-------|------|
| **API 응답** | 50ms | 50ms | 동일 (Redis Stream 사용) |
| **DB 저장** | 100ms | 100ms | 동일 |
| **알림 전송** | 직접 호출 (1초) | Kafka Consumer (비동기) | ✅ 분리 |
| **로그 저장** | 없음 | Kafka Consumer (비동기) | ✅ 추가 기능 |
| **통계 집계** | 없음 | Kafka Consumer (비동기) | ✅ 추가 기능 |

**사용자 경험**: 동일 (Redis Stream 유지)
**시스템 기능**: 확장 (이벤트 배포 가능)

## 4. 병렬 처리 vs 순차 처리 성능

### 4.1 병렬 처리 (쿠폰 발급)

**시나리오**: 1,000명이 동시에 쿠폰 발급 요청

#### AS-IS (단일 Consumer)
```
처리 시간 = 1,000건 / 100 TPS = 10초
첫 번째 사용자: 0.01초 대기
마지막 사용자: 10초 대기
평균 대기 시간: 5초
```

#### TO-BE (파티션 3개, Consumer 3개)
```
처리 시간 = 1,000건 / 300 TPS = 3.33초
첫 번째 사용자: 0.01초 대기
마지막 사용자: 3.33초 대기
평균 대기 시간: 1.67초

개선: 70% 단축 (5초 → 1.67초)
```

### 4.2 순차 처리 (콘서트 대기열)

**시나리오**: 1,000명이 순차적으로 입장 (파티션 1개 고정)

```
처리 시간 = 1,000건 / 100 TPS = 10초
순서 보장: ✅ FIFO 보장
처리량: 100 TPS (확장 불가)

트레이드오프:
- 순서 보장 필수 → 파티션 1개 고정
- 처리량 제한 → Consumer 1개만 가능
- 공정성 보장 → 선착순 정확
```

## 8. 부하 테스트 시나리오 (TO-BE 측정 계획)

### 8.1 주문 API 부하 테스트

```bash
# 목표: 응답시간 1초 이내 유지
# 부하: 100 TPS → 500 TPS (5분간)

k6 run --vus 100 --duration 5m order-load-test.js

측정 항목:
- P50 응답시간: < 500ms (목표)
- P95 응답시간: < 1000ms (목표)
- P99 응답시간: < 2000ms (목표)
- 에러율: < 0.1% (목표)
```

### 8.2 쿠폰 발급 부하 테스트

```bash
# 목표: 300 TPS 이상 처리
# 부하: 1,000명 동시 요청 (선착순 100개)

k6 run --vus 1000 --iterations 1000 coupon-load-test.js

측정 항목:
- 처리량: > 300 TPS (목표)
- 성공률: 100건 정확히 발급
- 중복 발급: 0건 (목표)
- 평균 대기 시간: < 2초 (목표)
```

### 8.3 장애 복구 테스트

```bash
# 시나리오 1: Kafka 브로커 1대 다운
1. Kafka 브로커 1대 강제 종료
2. Outbox가 자동으로 재시도하는지 확인
3. 복구 시간 측정

측정 목표:
- 메시지 유실: 0건
- 복구 시간: < 5분
- 사용자 영향: 없음

# 시나리오 2: Consumer 장애
1. 알림 Consumer 강제 종료
2. 주문이 계속 처리되는지 확인
3. Consumer 재시작 후 메시지 처리 확인

측정 목표:
- 주문 처리: 정상
- 메시지 유실: 0건
- 장애 격리: 완벽
```

## 9. 성능 개선 로드맵

### Phase 1: 현재 (TO-BE 구현 완료)
- ✅ Kafka 기반 이벤트 아키텍처 구축

- ✅ 병렬/순차 처리 전략 구현
- ✅ 장애 격리 및 자동 재시도

### Phase 2: 단기 (1-2개월)
- 🎯 파티션 수 증가: 3개 → 6개 (처리량 2배)

### Phase 4: 장기 (6-12개월)
- 🎯 Event Sourcing 도입 (이벤트 기반 상태 관리)
